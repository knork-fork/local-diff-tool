# Local Code Review — Design & Technical Specification

## 1. Overview

A local-first code review application inspired by GitLab's Merge Request Changes interface, designed primarily for reviewing code generated by AI coding agents before committing or pushing changes to a remote repository.

The application provides a polished, browser-based interface for reviewing local Git diffs, leaving inline comments, managing discussion threads and tracking review progress.

It must operate independently of GitLab, GitHub or any other remote repository hosting service.

## 2. Objectives

- Provide a GitLab-quality code review experience for local, uncommitted changes.
- Enable systematic, file-by-file review of large changesets.
- Allow inline commenting and threaded discussions.
- Persist review progress across application restarts and code modifications.
- Support multiple local repositories through a single application instance.
- Store review metadata within each reviewed repository using Git-ignored JSON files.
- Provide a REST API that can later be used by AI coding agents.
- Require minimal setup and allow reviews to be opened directly from the terminal.

## 3. Technology Stack

| Component | Solution |
|---|---|
| Frontend | React + TypeScript |
| Diff rendering | Pierre Diffs or `react-diff-view` |
| Syntax highlighting | Shiki |
| File tree | Existing React tree component |
| Diff generation | Native Git CLI |
| Review persistence | Repository-local JSON files |
| Backend API | Local HTTP REST API |
| Deployment | Docker Compose |
| Installation | `setup.sh` |
| CLI launcher | Executable in `~/.local/bin/` |
| Browser integration | System default browser |
| Application port | `22222` |
| Optional separate backend port | `22223`, only if necessary |

Backend language, framework and specific frontend component libraries are implementation decisions. Existing libraries should be preferred over custom implementations where appropriate.

## 4. User Interface

### 4.1. Design principles

GitLab's Merge Request Changes interface should serve as the primary visual and UX reference.

The interface should prioritize:

- Code readability.
- Clear visual hierarchy.
- Efficient navigation between files.
- Compact but readable typography.
- Subtle diff background colors.
- Clearly distinguishable comments and discussions.
- Minimal visual clutter.
- Dark and light themes.

The application should resemble a mature code review product rather than an internal developer utility.

### 4.2. Application header

The header should display:

- Repository name.
- Current Git branch.
- Number of changed files.
- Number of added and removed lines.
- Review progress.
- Number of unresolved discussions.

Available actions should include:

- Refresh diff.
- Switch between unified and side-by-side diff.
- Change diff scope.
- Export review comments.
- Submit review.
- Application settings.

### 4.3. File navigation sidebar

A persistent, independently scrollable sidebar containing a hierarchical tree of changed files.

Each file entry should display:

- Filename.
- Change type: added, modified, deleted or renamed.
- Added and removed line counts.
- Reviewed status.
- Unresolved comment count.

The sidebar should support:

- Collapsible directories.
- Filename and path filtering.
- Filtering reviewed and unreviewed files.
- Clear highlighting of the currently selected file.

Selecting a file must display only that file's diff.

**The file tree must function as a file selector, not as a table of contents for one large, continuously rendered diff.**

### 4.4. Diff viewer

The main content area displays the selected file.

Requirements:

- Unified and side-by-side diff modes.
- Syntax highlighting.
- Old and new line numbers.
- Clearly distinguishable additions and deletions.
- Collapsible unchanged sections.
- Expandable surrounding context.
- Ability to display the entire file.
- Horizontal scrolling for long lines.
- Inline comment creation.
- Inline discussion threads.
- Mark file as reviewed.
- Previous and next file navigation.
- Navigate to the next unreviewed file.

Only the selected file's diff should be fetched and rendered. Loading a repository must not require fetching or rendering every changed file's full diff.

Binary files should display an appropriate summary instead of attempting to render a textual diff.

### 4.5. Comments and discussions

Users must be able to create comments directly on lines of code, including added and removed lines.

A discussion should support:

- Single-line and multi-line comments.
- Markdown content.
- Multiple replies.
- Editing comments.
- Deleting comments.
- Resolving discussions.
- Reopening resolved discussions.
- Identifying outdated discussions.

Discussion threads should appear directly beneath the associated code, following GitLab's presentation.

Comments must remain accessible even if their original code is subsequently modified or removed.

### 4.6. Review progress

Users must be able to mark individual files as reviewed.

Review progress should be displayed globally, for example:

`12/41 files reviewed · 8 unresolved discussions`

Marking a file as reviewed must not modify Git state or automatically stage the file.

If a previously reviewed file changes, its reviewed status must automatically become invalid upon the next refresh.

### 4.7. Review submission

Users should be able to accumulate comments throughout a review and submit them as a batch.

Submitting a review should:

- Persist the review and its comments.
- Make submitted comments available through the REST API.
- Allow exporting feedback as structured JSON or human-readable Markdown.
- Provide a convenient copy-to-clipboard action.

Submitting a review must not commit, stage or push code.

No automatic interaction with coding agents is required at this stage.

## 5. Git Integration

### 5.1. Diff scopes

The application should support the following scopes:

| Scope | Git equivalent |
|---|---|
| Unstaged changes | `git diff` |
| Staged changes | `git diff --cached` |
| All uncommitted changes | `git diff HEAD` |
| Untracked files | Separate discovery and diff generation |

The default scope should be unstaged changes, including untracked files.

Untracked files should be presented as newly added files.

Repositories without an initial commit should also be supported.

The application's metadata directory must never appear in the changed-file tree or generated diffs.

### 5.2. Repository operations

All Git operations should be performed using the native Git CLI.

The backend should:

- Resolve the repository root.
- Determine the current branch.
- Retrieve changed file metadata independently of full file diffs.
- Retrieve individual file diffs on demand.
- Detect added, modified, deleted, renamed and untracked files.
- Calculate file or diff fingerprints for review invalidation.
- Support Git worktrees.

Git operations must be read-only, with the sole exception of configuring the local exclusion of the application's metadata directory during repository initialization.

The application must not stage, commit, reset, checkout or otherwise modify source code or Git history.

### 5.3. Refresh behavior

The application should provide an explicit refresh action that:

1. Retrieves the current repository state.
2. Updates the changed file tree.
3. Invalidates reviewed status for modified files.
4. Re-evaluates comment positioning.
5. Marks discussions as outdated when necessary.
6. Preserves existing review data.

No filesystem watchers, WebSockets, SSE or live updates are required.

## 6. Architecture

The application consists of a React frontend, a local REST API backend, native Git integration and repository-local JSON persistence.

```text
                    Host machine

    CLI launcher
         │
         ├── Ensure Docker Compose is running
         ├── Initialize repository metadata
         ├── Register repository via REST API
         └── Open browser
                  │
                  ▼
         localhost:22222
                  │
    ┌─────────────┴─────────────────────┐
    │          Docker Compose           │
    │                                   │
    │   React frontend                  │
    │         │                         │
    │         ▼ /api/*                  │
    │   REST API backend                │
    │       │         │                 │
    │       ▼         ▼                 │
    │    Git CLI   JSON persistence     │
    └───────┬─────────┬─────────────────┘
            │         │
            ▼         ▼
    ┌───────────────────────────────────┐
    │       Mounted host repository     │
    │                                   │
    │   .git/                           │
    │   src/                            │
    │   .local-review/review.json       │
    └───────────────────────────────────┘
```

### 6.1. Request flow

- The browser communicates with the backend through the REST API.
- The backend executes read-only Git commands against the selected repository.
- The backend reads and writes review JSON files located within the selected repository's metadata directory.
- The frontend renders repository metadata, individual file diffs and review state.

A single running application instance must support multiple repositories independently.

### 6.2. HTTP architecture and ports

The application should expose a single HTTP endpoint whenever possible:

`http://localhost:22222`

| Route | Purpose |
|---|---|
| `/` | React frontend |
| `/api/*` | REST API |
| `/api/health` | Application health check |

The preferred architecture is to serve the compiled React frontend and REST API from the same HTTP server.

If the frontend and backend are implemented as separate services, the frontend-facing server should proxy `/api/*` requests to the backend over the internal Docker network.

A separate host-exposed backend port should not be introduced unless technically necessary.

If a separate backend port is necessary, port `22223` must be used.

| Port | Purpose | Requirement |
|---|---|---|
| `22222` | Frontend and preferably REST API | Required |
| `22223` | Separately exposed backend | Optional, only if necessary |

All host-exposed ports must be bound to localhost.

The frontend should use relative API URLs under `/api/` in the preferred single-port configuration.

## 7. Persistence

### 7.1. Storage

Review data must be stored in JSON files within each reviewed repository.

A dedicated metadata directory should be created in the repository root.

Provisional directory name: `.local-review/`.

Example:

```text
my-repository/
├── .git/
├── .gitignore
├── .local-review/
│   └── review.json
├── src/
├── tests/
└── README.md
```

Each repository must contain its own independent review metadata.

Requirements:

- Metadata must be stored directly on the host filesystem.
- The metadata directory must be accessible and writable from inside the container.
- The metadata directory must be Git-ignored.
- Metadata must never appear in the application's own diff viewer.
- Review data must survive container restarts, rebuilds and application upgrades.
- Separate Git worktrees should maintain independent review metadata.
- No centralized review storage directory.
- No database.
- No Docker-managed persistence volume for review data.

### 7.2. Git exclusion

When initializing a repository, the CLI launcher must ensure that `.local-review/` is excluded from Git tracking.

If the directory is already covered by an existing ignore rule, no additional changes are necessary.

Otherwise, the launcher should add the exclusion to the repository's local Git exclude file, resolved using:

```bash
git rev-parse --git-path info/exclude
```

The exclusion should be added idempotently.

This avoids modifying the repository's tracked `.gitignore` file and introducing unrelated changes into the review.

### 7.3. Data model

Each repository's JSON file should contain:

| Property | Description |
|---|---|
| `schemaVersion` | Persistence format version |
| `reviewedFiles` | Reviewed files and their fingerprints |
| `discussions` | Inline comments and discussion threads |
| `reviews` | Submitted review batches |
| `settings` | Repository-specific preferences |
| `createdAt` | Creation timestamp |
| `updatedAt` | Last modification timestamp |

Review state should be scoped by branch and diff scope within each repository file to prevent unrelated changes from inheriting previous review status.

Repository metadata should use relative file paths wherever possible.

### 7.4. Discussion data

Each discussion should contain:

- Unique identifier.
- Repository-relative file path.
- Original line number or line range.
- Diff side: old or new.
- Original code context.
- Original diff fingerprint.
- Comment body.
- Replies.
- Resolution status.
- Outdated status.
- Associated submitted review, if applicable.
- Creation and modification timestamps.

Stable identifiers must be used so discussions can later be referenced through external integrations.

### 7.5. Reviewed-file invalidation

When a file is marked as reviewed, its current diff fingerprint should be persisted.

On refresh, the backend compares the stored fingerprint against the current fingerprint.

If they differ, the file becomes unreviewed.

The fingerprint should represent the actual reviewed diff, rather than relying solely on file modification timestamps.

### 7.6. Comment anchoring

Comments should not rely exclusively on line numbers, since subsequent code modifications may shift their positions.

The backend should use the original line numbers and surrounding code context to attempt to relocate comments.

If a comment cannot be reliably relocated, it should be marked as outdated rather than silently attached to unrelated code or deleted.

### 7.7. Write safety

JSON persistence should support:

- Atomic writes using temporary files and rename operations.
- Protection against concurrent write conflicts.
- Schema versioning for future format migrations.
- Graceful handling of missing or malformed persistence files.

Malformed persistence files must not be silently overwritten.

## 8. REST API

The REST API should be designed independently of the frontend so that future AI agent integrations can reuse it.

The default API base URL is:

`http://localhost:22222/api`

Port `22223` should only be used if a separate backend endpoint is technically necessary.

Proposed endpoints:

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/health` | Application health check |
| POST | `/api/repositories/open` | Register or open a repository |
| GET | `/api/repositories` | List known repositories |
| GET | `/api/repositories/:id` | Repository metadata |
| GET | `/api/repositories/:id/files` | Changed file metadata |
| GET | `/api/repositories/:id/diff` | Individual file diff |
| POST | `/api/repositories/:id/refresh` | Refresh repository state |
| GET | `/api/repositories/:id/review` | Current review state |
| PUT | `/api/repositories/:id/files/reviewed` | Update reviewed status |
| GET | `/api/repositories/:id/discussions` | Retrieve discussions |
| POST | `/api/repositories/:id/discussions` | Create discussion |
| PATCH | `/api/repositories/:id/discussions/:discussionId` | Update discussion |
| DELETE | `/api/repositories/:id/discussions/:discussionId` | Delete discussion |
| POST | `/api/repositories/:id/discussions/:discussionId/replies` | Add reply |
| POST | `/api/repositories/:id/reviews` | Submit review |
| GET | `/api/repositories/:id/export` | Export review feedback |

The API should support filtering discussions by file, resolution status, outdated status and submission status.

All API responses should use structured JSON, except where another export format is explicitly requested.

The endpoint structure is provisional and may be adjusted during implementation.

## 9. Docker Deployment

The entire application must be deployable using Docker Compose.

### 9.1. Requirements

- All application services defined in `docker-compose.yml`.
- No host-side Node.js or backend runtime installation required.
- Git installed inside the backend container.
- Application exposed on host port `22222`.
- Backend port `22223` exposed only if necessary.
- All HTTP endpoints bound to localhost only.
- Container processes running without unnecessary root privileges.
- Host repositories accessible through bind mounts.
- Repository-local review metadata accessible and writable from inside the container.
- No separate database or persistence service.

### 9.2. Filesystem access

The user's home directory should be mounted into the container with read-write permissions to allow reviewing arbitrary repositories and writing repository-local metadata without recreating containers.

Example Compose configuration:

```yaml
services:
  app:
    build: .
    ports:
      - "127.0.0.1:22222:22222"
    volumes:
      - "${HOME}:/host/home:rw"
    environment:
      HOST_HOME: ${HOME}
      MOUNTED_HOME: /host/home
      APP_PORT: 22222
    user: "${HOST_UID}:${HOST_GID}"
    restart: unless-stopped
```

This configuration assumes a single application service serving both the frontend and REST API.

If separate frontend and backend containers are used, the backend should communicate through the internal Docker network without publishing an additional host port. Only publish `127.0.0.1:22223` if direct backend exposure is technically necessary.

Although the home directory mount is writable, application-level restrictions must ensure that:

- Source code is only read.
- Git commands do not modify repository contents or history.
- Application writes are restricted to the `.local-review/` directory.
- Requested repository paths are validated and normalized.
- File operations cannot escape the intended repository or metadata directory through path traversal or symbolic links.
- Git commands use argument arrays rather than interpolating user-supplied paths into shell commands.

Repositories located outside the user's home directory should require an explicitly configured additional mount.

Repository paths must be consistently mapped between the host and container.

### 9.3. Mounting rationale

Docker does not support dynamically adding bind mounts to running containers.

Mounting each repository as read-only and separately mounting its metadata directory as writable would require container recreation whenever a new repository is introduced.

A shared read-write home directory mount avoids this complexity and allows one application instance to handle multiple repositories while keeping review metadata repository-local.

This means that write restrictions are enforced by the application rather than by Docker filesystem permissions.

### 9.4. Application lifecycle

A single application instance should remain available for reviewing multiple repositories.

Opening another repository must not require starting an additional container or application instance, provided the repository is already within a mounted directory.

Container rebuilds and application upgrades must not affect repository-local review data.

## 10. Installation Script

A `setup.sh` script should provide initial installation and configuration.

The script should:

1. Verify that Docker and Docker Compose are available.
2. Determine the current user's home directory, UID and GID.
3. Configure Docker Compose environment variables and filesystem mounts.
4. Check whether the required host port is available.
5. Build the application containers.
6. Start the application.
7. Create `~/.local/bin/` if necessary.
8. Install an executable launcher into `~/.local/bin/`.
9. Ensure or provide instructions for adding `~/.local/bin/` to the user's PATH.
10. Verify that the application is reachable through `http://localhost:22222/api/health`.

If a separate backend port is required, the script should also verify availability of port `22223` and check the corresponding backend health endpoint.

The script should report port conflicts clearly rather than silently selecting different ports.

The script should be idempotent and must not overwrite existing review data when executed again.

The script should not create centralized review persistence directories. Repository metadata is initialized individually when a repository is opened for review.

## 11. CLI Launcher

A lightweight shell executable should be installed into `~/.local/bin/`.

Provisional command name: `review`.

### 11.1. Usage

Review the current repository:

```bash
review
```

Review a specific repository:

```bash
review ~/projects/my-repo
```

Review a repository using a relative path:

```bash
review ../another-repo
```

The command should also work when executed from a subdirectory within a Git repository.

### 11.2. Execution flow

The launcher should:

1. Accept an optional repository path.
2. Default to the current working directory.
3. Resolve the absolute path and Git repository root.
4. Validate that the target is a Git repository.
5. Create `.local-review/` if it does not exist.
6. Ensure `.local-review/` is Git-ignored.
7. Ensure the repository and its metadata directory are accessible to the container.
8. Start the Docker Compose application if it is not already running.
9. Wait until the local API is reachable.
10. Register or open the repository through the API.
11. Open the corresponding review page in the system's default browser.

The launcher must work independently of the directory from which it is executed.

It should retain a reference to the application installation directory so Docker Compose commands are executed against the correct configuration.

### 11.3. Application URLs

The launcher should use the following endpoint to register repositories:

`POST http://localhost:22222/api/repositories/open`

The backend should return the repository identifier and corresponding review URL.

Example browser destination:

`http://localhost:22222/repositories/<repository-id>`

If a separate backend port is required, the launcher should use port `22223` for API requests while continuing to open the frontend on port `22222`.

### 11.4. Error handling

The launcher should provide clear error messages for:

- Invalid repositories.
- Inaccessible paths.
- Metadata directory permission errors.
- Repositories outside configured mounts.
- Unavailable Docker services.
- Application startup failures.
- Port conflicts.
- API connectivity failures.
- Browser launch failures.

## 12. Intended User Workflow

1. The developer or coding agent modifies a local repository.
2. The developer executes `review` from the repository directory.
3. The launcher initializes repository-local metadata if necessary.
4. The application opens in the browser on port `22222` and displays changed files.
5. The developer selects a file and reviews its diff.
6. The developer leaves inline comments where necessary.
7. The developer marks reviewed files and proceeds to the next file.
8. The developer submits or exports review feedback.
9. The coding agent receives feedback manually and modifies the code.
10. The developer refreshes the review.
11. Modified files become unreviewed, and affected discussions are marked outdated where appropriate.
12. The review continues until the developer is satisfied.
13. The developer commits and pushes changes through their normal Git workflow.

All review metadata remains in the repository's Git-ignored `.local-review/` directory throughout the process.

## 13. Future Extensibility

The architecture should allow future integration with AI coding agents without requiring major changes to the frontend, persistence format or core review logic.

Potential future features:

- MCP server exposing review operations.
- Claude Code integration.
- Agent replies to discussion threads.
- Agent acknowledgement of addressed comments.
- Automatic review submission to an existing agent session.
- Comparison between successive review iterations.

These features must not be implemented as part of the initial version.

## 14. Out of Scope

- MCP server.
- Claude Code or other coding agent integrations.
- Embedded terminal.
- Live updates.
- Filesystem watchers.
- WebSockets or SSE.
- Database.
- Centralized review persistence.
- Authentication and user management.
- Multi-user collaboration.
- Remote repository synchronization.
- GitLab or GitHub integrations.
- Staging, committing or pushing changes.
- Repository hosting.
- Merge management.
- CI/CD integration.
- Automated AI code reviews.

- [ ] Multiple repositories can be reviewed using a single application instance.
